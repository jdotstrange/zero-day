Engineer Handbook

What You Got

0-Day is a line-of-business admin UI shell: a client-rendered Vite SPA (React 19 + TypeScript + Tailwind CSS 4 + React Router) scaffolded from an internal factory template. It is the front end only — auth, APIs, and background workers live on Azure and get wired in by you, later.

Who this is for: engineers who inherited a baked client repo produced by the scaffold, or who are exploring the factory template itself. If you are reading this inside the factory repo, the app root is zero-day/; in a baked client repo, the app is the repo root. All src/… paths below are relative to that app root.

The product (in the nav)

A lean shell: the dashboards, starter modules, and advanced features selected at scaffold time, plus Account Settings. / redirects to the first selected dashboard. There is no marketing landing page in the product path.

The kit (on disk)

Everything else stays on disk and routable by direct URL: forms, tables, charts, pricing, gallery, FAQ, typography, the alternate auth layout, and landing-page sections. Promote pieces into the nav when the client needs them; prune when you're sure they never will.

Tech stack

React 19 TypeScript Vite Tailwind CSS 4 React Router Chart.js DND Kit Tiptap

Exact versions live in package.json. Not Next.js — no server rendering, no server components.

Run It

Node 18+ and npm 9+ (see engines in package.json). No environment variables and no backend are needed — every screen runs on mock data.

npm install
npm run dev      # dev server on http://localhost:5173
npm run build    # type-check (tsc -b) + production build to dist/
npm run preview  # serve the built dist/ locally
npm run lint     # eslint

Build = type-check. npm run build runs tsc -b before Vite, so type errors fail the build. That is intentional — don't work around it with @ts-nocheck.

Promote a kit page

Add an entry to src/layouts/sidebar/navData.ts. The route already exists; nav is the only gate.

Prune a kit page

Remove the lazy import and route entry from src/routes/index.tsx, then delete the page component. Only do this when the client will genuinely never need it.

Brand & Theme

Branding is two independent levers: logo files (drop-in, no code) and theme colors (CSS variables plus a baked brand preset).

Logos — replace files in place, no code changes

File (public/assets/logo/) Used for
logo.svgWordmark on light backgrounds (sidebar/header, light mode)
logo-dark.svgWordmark on dark backgrounds (auth panel, dark mode)
logomark.svgIcon-only mark (collapsed sidebar, favicon via index.html)

Keep filenames and rough SVG dimensions. The Logo component and auth layouts read this folder automatically; see public/assets/logo/README.md.

Colors — CSS variables + brand preset

Primary and accent are CSS variables holding space-separated RGB channels (e.g. 59 130 246, not hex), consumed as rgb(var(--theme-primary) / <alpha>). In a baked repo the scaffold's chosen colors are installed as a brand preset and set as the default. To change them, update all three in sync:

  1. src/styles/variables.css — --theme-primary / --theme-accent
  2. src/types/theme.ts — themeColorPresets entry for the active defaultThemeConfig.color
  3. index.html — the inline boot script's presets object (prevents a flash of wrong colors before React mounts)

Light + dark both ship

Users toggle surface in the header. The default surface (what an empty browser sees first) was baked into defaultThemeConfig.mode in src/types/theme.ts. User choice persists in localStorage under <package-name>-theme (the npm name in package.json).

No end-user theme panel

A ThemeCustomizer component exists on disk but is deliberately unmounted. Clients get the baked brand, not a theme picker. Mount it in RootLayout only if a client explicitly wants runtime theme switching.

Authentication

0-Day ships a config-driven auth kit under src/auth/. The login UI is composed from config; a single adapter field chooses how sessions are established. Fresh scaffolds always start on the mock adapter so the admin shell works day zero with no env and no backend.

Mental model: methods / primary control what the login page shows; adapter controls what actually runs. The kit (adapters, RequireAuth, session context) is always on disk — config only chooses the front face and the live implementation.

The config file — src/auth/config.ts

export const authConfig: AuthUiConfig = {
  methods: ['credentials'],       // which sign-in UIs to show
  primary: 'credentials',         // rendered first on LoginPage
  registerEnabled: true,          // login footer + RegisterPage gate (template on-disk)
  passwordlessMode: 'otp',        // 'otp' | 'magic-link'
  socialProviders: ['google', 'apple'],
  adapter: 'mock',                // ALWAYS 'mock' on a fresh scaffold
  postLoginPath: '/dashboard',    // fallback when no return URL
}

The scaffold interview regenerates this object wholesale (methods, primary, register, passwordless mode, social providers, post-login path). Types above the const stay put. Values above are the template's on-disk defaults; bake writes registerEnabled from the interview (default no). Your baked repo may differ, but adapter is always 'mock' until you change it.

Demo credentials (mock)

  • Any email + password signs in
  • OTP code is 000000
  • Session persists in localStorage (zeroday-auth-session)
  • Logout clears it; refresh keeps you signed in

Login UI composition

LoginPage renders only the methods listed in config, primary first. SSO-only (methods: ['entra']) is a single Microsoft button — no email fields. Register footer appears only when registerEnabled is true and credentials or passwordless is enabled.

Going live — one-line adapter switch

Set adapter to the implementation you want, keep methods aligned with what that adapter can handle, then wire (or configure) it:

Adapter What you do
credentials Implement the stub in adapters/credentials.ts against your login API. Until wired, every method throws credentials adapter not wired.
passwordless Same pattern in adapters/passwordless.ts — handle passwordless-request and passwordless-verify (OTP or magic-link per config).
oauth Wire adapters/oauth.ts for Google / Apple / GitHub (or your IdP). Driven by socialProviders.
entra Real MSAL adapter (@azure/msal-browser). Set VITE_AZURE_CLIENT_ID + VITE_AZURE_TENANT_ID; optional VITE_AZURE_REDIRECT_URI (defaults to window.location.origin). Register that URI on the Azure app. Uses loginPopup — for redirect, swap to loginRedirect / handleRedirectPromise (noted in the adapter source).

Adapter interface

interface AuthAdapter {
  id: AdapterId
  signIn(input: SignInInput): Promise<AuthSession>
  signOut(): Promise<void>
  getSession(): Promise<AuthSession | null>
  onSessionChange(cb: (s: AuthSession | null) => void): () => void
}

type SignInInput =
  | { method: 'credentials'; email: string; password: string }
  | { method: 'passwordless-request'; email: string }
  | { method: 'passwordless-verify'; email: string; code: string }
  | { method: 'social'; provider: 'google' | 'apple' | 'github' }
  | { method: 'entra' }

Defined in src/auth/types.ts. Registry: getAdapter(id) in src/auth/adapters/index.ts. AuthProvider resolves the live adapter once from authConfig.adapter.

Session — useAuth()

From src/hooks/useAuth.ts: session, status (loading | authenticated | unauthenticated), signIn, signOut. Must be under AuthProvider.

Route guard — RequireAuth

Wraps the admin route tree in src/routes/index.tsx. Unauthenticated visitors go to /auth/login with state.from set so login can return them. If there is no return URL, login falls back to authConfig.postLoginPath.

Gotchas

  • Missing Azure env throws a descriptive error only when the entra adapter is invoked (sign-in / MSAL init) — never at import time while adapter: 'mock'.
  • With registerEnabled: false, RegisterPage redirects to login; the route still exists.
  • Both auth layout trees remain available: /auth/* (split) and /auth-card/* (card). See Auth Screens.

Auth Screens

Two layout route trees for login, register, and forgot-password. The forms themselves are config-driven and backed by the auth kit (working mock adapter by default) — see Authentication for session, adapters, and going live.

Split layout — /auth/*

Side-by-side layout: brand panel on one half, form on the other (AuthLayout).

Card layout — /auth-card/*

Centered single card (AuthCardLayout).

What the scaffold baked

  • One layout was chosen as the live prefix; all login/logout/forgot links point at it. Both route trees still exist — the other layout stays reachable by direct URL as kit.
  • Login and forgot-password are always linked.
  • Register is optional: the route always exists, but the "create account" link appears only when registerEnabled is true (set at scaffold time). Flip it later in src/auth/config.ts.
  • Successful login returns to the intended route (state.from) when present, otherwise authConfig.postLoginPath.

i18n — English-first

The i18n plumbing is kept but the product ships English-first; treat en.json as the source of truth for UI copy. To add a language: copy src/i18n/locales/en.json to a new locale file and register it in src/i18n/index.ts. The app defaults to left-to-right; don't change the direction default.

Env & Azure Handoff

The shell runs with zero environment variables out of the box — screens use mock data in src/data/, and the auth kit ships with adapter: 'mock'. Real APIs and workers are the client's Azure estate; Entra is ready when you flip the adapter and set env (see Authentication).

When you wire the backend

  • Vite only exposes variables prefixed VITE_ to client code (via import.meta.env). Convention for the API entry point: VITE_API_BASE_URL pointing at the client's Azure API (App Service, Container Apps, or API Management front door).
  • Identity is typically Microsoft Entra ID. @azure/msal-browser ships in the template and the entra adapter is real — env-gated behind VITE_AZURE_CLIENT_ID, VITE_AZURE_TENANT_ID, and optional VITE_AZURE_REDIRECT_URI. The bake still leaves adapter: 'mock'; switch to 'entra' when the client's app registration exists. Don't ship the mock's localStorage session to production.
  • Replace mock reads screen by screen: swap the src/data/ imports in a page for real fetches. The UI contracts (types in src/types/) tell you what shape the API needs to produce.
  • Anything secret does not belong in a VITE_ variable — it ships to the browser. Secrets stay behind the Azure API.

Deploying the SPA

npm run build emits a static dist/. Host it on anything static (Azure Static Web Apps, Storage + CDN, App Service). The host must serve index.html for unknown paths (SPA fallback) or deep links and refreshes will 404.

Troubleshooting

The issues engineers actually hit with this shell.

Theme or colors don't match what the scaffold configured

Stale localStorage overrides baked defaults. Clear the <package-name>-theme key (and <package-name>-locale if relevant) in DevTools → Application → Local Storage, then reload. With empty storage, the boot script in index.html does nothing and defaultThemeConfig is the source of truth.

A page exists on disk but isn't in the sidebar

Expected. Nav controls visibility, not routing — the whole kit stays routable at direct URLs. Add an entry to src/layouts/sidebar/navData.ts to surface it. See Product vs Kit.

Blank page or 404s after npm run build

Configure SPA fallback: the host must serve index.html for all app routes. If deploying under a sub-path, also set base in vite.config.ts.

Port 5173 is already in use

Another Vite dev server is running. Stop it, or run npm run dev -- --port 3000.

"Unsupported engine" warnings on install

Node 18+ and npm 9+ are required (engines in package.json). Check with node -v; Node 20 LTS is the safe pick.

Build fails with TypeScript errors

npm run build runs tsc -b first, so any type error anywhere fails the build — including feature engine files under src/features/. Fix the types; don't suppress with @ts-nocheck.

Dependency versions drift between machines

Use npm ci instead of npm install to install exactly what package-lock.json pins. Delete node_modules first if a plain install already ran.
